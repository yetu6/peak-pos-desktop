# Peak POS Phase 3 Local Transaction Store Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Establish the Rust-owned, SQLCipher-encrypted transactional store boundary, schema migrations, safe health command, key rotation/recovery workflow, and integrity evidence required by Phase 3.

**Architecture:** A synchronous `rusqlite` connection lives exclusively in Rust behind Tauri managed state. A device-local 256-bit database key is generated by the OS CSPRNG and stored as a versioned envelope in the OS keyring; React receives only a redacted health result through one narrow command. Migration, encryption verification, integrity checking, key rotation, and recovery are tested without implementing catalog ingestion, order mutations, settlement, synchronization, or printing behavior.

**Tech Stack:** Rust 2021, Tauri 2, rusqlite 0.40.2, bundled SQLCipher with vendored OpenSSL, keyring 3, getrandom 0.4.3, base64 0.23.1, SHA-256, zeroize, tempfile-based Rust integration tests.

**Spec:** `docs/PEAK_POS_DESKTOP_MASTER_OPERATIONS.md` §§10–13, 20–21 and `docs/PEAK_POS_DESKTOP_OFFLINE_SAFETY_MATRIX.md`

## Global Constraints

- Rust is the only owner of the local database; React receives no SQL, connection, table, or arbitrary query interface.
- SQLCipher is mandatory; plaintext production fallback and homemade encryption are prohibited.
- An existing database with a missing, inaccessible, malformed, or mismatched production key fails closed and is preserved.
- Keys, PIN material, payloads, SQL errors, and raw cryptographic diagnostics never cross IPC.
- Phase 3 does not implement offline orders, cash settlement, catalog synchronization, leases, reconciliation, printing protocol, or backend migrations.
- PostgreSQL remains the post-reconciliation system of record; the local schema established here is infrastructure, not a claim that later protocols are implemented.
- No merge or deployment is authorized.

- [x] **Step 1: Write failing rotation tests**

- [x] **Step 2: Run focused tests and confirm rotation is absent**

- [x] **Step 3: Implement prepare/rekey/verify/promote**

Checkpoint WAL, make an owner-only encrypted recovery copy, save an envelope containing current and next keys with `PREPARED` state, acquire exclusive access, execute SQLCipher rekey, reopen with the next key, run both integrity checks, atomically promote the next key envelope, and only then remove the recovery copy.

- [x] **Step 4: Implement restart recovery**

When a prepared envelope is found, try the next key first and promote it if healthy; otherwise reopen with the current key and complete the same rekey workflow. If neither key opens, preserve the database and recovery copy and return a redacted failure without silently restoring or replacing evidence.

- [x] **Step 5: Verify all recovery tests**

Run the complete Rust suite and require every interruption boundary to preserve at least one decryptable database/key pair.
